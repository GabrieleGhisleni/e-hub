## Findings

### R1-01 · medium · `src/node/site-data/markdown.ts:12` (sink: `src/web/routes/book-page.tsx:306,322`)

**Problem.** The Markdown renderer escapes raw HTML but passes link and image URLs through unchanged, so `javascript:` and `data:` URLs reach `dangerouslySetInnerHTML`.

**Failure scenario.** `notes.md` / `recall.md` / `study.md` contains `[vedi](javascript:fetch('/api/books/<id>',{method:'DELETE'}))`. Such a file can come from an agent working on book text or highlights, which can carry a prompt injection. On the public site, clicking the link runs script on the shared `<user>.github.io` origin. In the local dev UI (`127.0.0.1:5173`), the same click runs in an origin that is in `server.allowedOrigins`, so the script passes every Origin, Host and Sec-Fetch-Site check (the call is same-origin through the Vite proxy). It can then delete books and trash their Drive files. This breaks W2c's stated guarantee that the published HTML "cannot carry scripts".

**Verified.** Scratch script (temp dir) running `renderMarkdown`. `[click](javascript:alert(1))` → `<a href="javascript:alert(1)">`, `JAVASCRIPT:` (any case) → kept, `![x](javascript:…)` → `<img src="javascript:…">`, `data:text/html;base64,…` → kept, reference-style `[ref]: javascript:…` → kept. Raw `<script>` and `<img onerror>` are correctly escaped.

**Fix.** Add `link` and `image` renderer overrides, or a `walkTokens` pass, that allow only `http:`, `https:`, `mailto:`, relative URLs and `#fragment`, and otherwise render the text without a link. Add tests for each case above. Optionally add a CSP meta tag to `index.html` (`script-src 'self'`; the inline theme script needs a hash).

### R1-02 · medium · `src/node/drive/plan.ts:288-317`, `src/node/cli/commands/sync.ts:16-26`

**Problem.** `elib sync --prune` treats as an orphan every Drive file whose ID has no folder in the data dir it happens to read, and nothing limits how many files it trashes.

**Failure scenario.** In each of these cases the whole library goes to the Drive trash with no warning beyond the generic `--prune` notice: a shell with a stale `ELIB_DATA_DIR` (the workflow documented for the demo data is `ELIB_DATA_DIR=/tmp/elib-demo-data …`), a fresh clone or an old branch or stash checked out, or a `data/books/` that is temporarily empty. The trash empties itself after 30 days, and Drive is the only durable copy (PLAN §14). The command never shows which data dir it used.

**Verified.** Scratch script with the local-remote helpers: 3 books created (6 Drive files), then `reconcile(drive, "all", { prune: true })` with the same config and a data dir holding only `topics.json`. Result: 6 `trash` actions `done`, 0 errors, remote empty.

**Fix.** (a) Print the data dir and the number of books read in every `sync` report. (b) Refuse a real `--prune` when the repo has 0 books, or when the files to trash exceed a threshold (for example more than 10 files or more than 20% of the recognized files), unless `--force` / `--yes` is given. Point the user at `--dry-run`. (c) Optionally require `--prune` to follow a `--dry-run` of the same plan, for example by printing a plan hash to pass back.

### R1-03 · medium · `src/node/services/import.ts:205-220` (with `uploads.ts:397-404` via `import.ts:294`)

**Problem.** A real `elib import` run that fails half-way leaves the EPUB on Drive as an orphan and discards the staging and cache. Every later run then sees that orphan's MD5 and skips the book as a "duplicate", so the book is never imported.

**Failure scenario.** During Fase 5 a KEPUB upload fails (network hiccup, Drive quota). `importOne` → `discardUpload` → `removeStaging` removes the cached EPUB/KEPUB and the cover-only folder. The EPUB stays in `Archivio/Da smistare/… [id].epub` with no repo folder. Re-running `elib import <folder>` reports `skipped …: same file already on Drive` for that book, and the summary counts it as "duplicate(s) skipped". The user believes it is already in the library, but `data/books/` has no such book. Only a `--prune` (or a manual delete) followed by another import recovers it.

**Verified.** Scratch script: `failingKepubRclone` (from `test/node/services/setup.ts`) for run 1 → status `failed`, remote holds only the EPUB, repo empty. Run 2 with the normal rclone on the same folder → status `duplicate`, `bookId` = the orphan ID, repo still empty.

**Fix.** In `importOne` (and in the upload form's `duplicates`), treat an MD5 match whose `bookId` is null or has no `data/books/<id>/` folder as an orphan. Do not skip it: either reuse that ID (`createBook` would then find the file already uploaded) or import it normally with a warning ("orphan copy on Drive, `elib sync --prune` will trash it"). Alternatively, on import failure keep the staging and reserved ID (do not `discardUpload`) so a rerun reuses the same ID, as `createBook` retries already do.

### R1-04 · medium · `src/node/epub/index.ts:85-110`, `src/node/text/structure.ts:129`

**Problem.** No size limit is applied when unzipping. `fflate.unzipSync` allocates the _declared_ uncompressed size of each entry and inflates into it, and `structure.ts` inflates every entry at once. A small EPUB can therefore make the server or CLI allocate gigabytes.

**Failure scenario.** A malformed or malicious EPUB from a shady download has a `META-INF/container.xml` that declares and expands to around 1 GB, or up to around 4 GB (zip64: more). `POST /api/uploads` or `elib import`/`elib text` reads it. RSS jumps by the declared size, the process may be OOM-killed (the server would die mid-request, possibly during another write), and otherwise the request ends in a 500 `internal-error`, because the non-`EpubError` `RangeError` is rethrown instead of becoming 400 `not-an-epub`.

**Verified.** Scratch script: a 1 MB EPUB whose container.xml expands to 1000 MB (built with Python `zipfile`). `extractEpubMetadata` took 3.6 s, peak RSS 1143 MB, and threw `Error: Cannot create a string longer than 0x1fffffe8 characters`, which is not an `EpubError`. fast-xml-parser 5.12 entity expansion was also probed: it is bounded (`maxExpandedLength` 100000 and no `&` allowed inside entities), so that path is fine.

**Fix.** In `openZip`, keep `originalSize` from the filter callback and refuse to read an entry above a cap (for example 16 MB for XML/XHTML/NCX and 50 MB for images), plus a total cap. In `structure.ts`, use the same filtered reader instead of `unzipSync(input)` on everything. Wrap any non-`EpubError` thrown while parsing in `EpubError("invalid-opf"…)` so the API answers 400.

### R1-05 · low · `src/node/services/uploads.ts:397-404`

**Problem.** `removeStaging` deletes `<cache>/books/<id>/` whenever `book.json` is missing, even when the staging `state.status` is `created`. That covers a book that was created and then deleted, whose cache copy `deleteBook` keeps on purpose ("last local copy while the Drive trash keeps 30 days").

**Failure scenario.** The user creates a book and deletes it the same day. At the next server start more than 24 h later, `cleanupStaleUploads` (or a `DELETE /api/uploads/:id` from the still-open form) wipes the cached EPUB and KEPUB. The last local copy is gone and the book ID is free for reuse while its files still sit in the Drive trash.

**Verified.** Scratch script: create, then `deleteBook` (cache still holds `book.epub` and `book.kepub.epub`), then `cleanupStaleUploads` with `now` +25 h. The cache dir is `MISSING`.

**Fix.** In `removeStaging`, clean the cache and the cover-only folder only when `state.status === "reserved"`.

### R1-06 · low · `src/node/vite/elib-data.ts:60`

**Problem.** The dev data middleware calls `decodeURIComponent` outside its `try` inside an `async` connect handler. A malformed escape becomes an unhandled rejection and kills the Vite dev server process.

**Failure scenario.** Any page open in the browser (or a typo) requests `http://127.0.0.1:5173/e-library/%E0%A4%A`, for example `<img src=…>` from a foreign site: Vite's host check passes and nothing blocks a GET. `pnpm dev` dies with `URIError: URI malformed` (exit 1), which also takes down the admin UI in the middle of the user's work.

**Verified.** Scratch script: programmatic `createServer` with `elibData`. `/e-library/data/index.json` → 200, then the malformed URL → the process exits with code 1 and the stack trace points at `elib-data.ts:60`.

**Fix.** Move the decode inside the `try`, or `try { decodeURIComponent } catch { return next(); }`, and add a test.

### R1-07 · low · `src/node/config/index.ts:73-76`, `src/shared/config.ts` (`cache.dir`)

**Problem.** Nothing stops `cache.dir` (or `ELIB_CACHE_DIR`) from pointing inside the repo, and a relative `cache.dir` resolves against the config file's folder, which is the repo root. The only guard is `assertOutsideRepo` in `elib text`.

**Failure scenario.** Someone sets `"cache": {"dir": ".cache/e-library"}`, which is a natural edit. Every upload then writes `book.epub`, `book.kepub.epub`, `upload.epub` and the staging JSON under the repo, and `.gitignore` does not cover them. A `git add -A` publishes copyrighted EPUBs in the public repo (PLAN §2, §5, §14), and a `git clean -fdx` wipes the cache. `validate:data` only checks `data/`, and the CI guard catches only `*.epub` (not `*.EPUB`, not staging JSON).

**Verified.** By reading the code (no repro: it would mean editing the real config).

**Fix.** In `loadConfig`, reject a cache dir equal to or inside `REPO_ROOT`: reuse `assertOutsideRepo`'s realpath logic in a sync version. Optionally make the CI guard case-insensitive (`git ls-files ':(icase)*.epub'`).

### R1-08 · low · `src/node/site-data/validate.ts:27-39`

**Problem.** The public-repo guard looks only at key _names_ (`/drive|md5|sha-?\d+|hash|path|fileId/i`). File identifiers stored under any other key, or inside a value, pass both `validate:data` and CI.

**Failure scenario.** A hand edit, or an agent following PLAN §5's "unknown fields are kept", adds `"link": "https://drive.google.com/file/d/<id>/view"`, `"file": "Archivio/…/x [id].epub"` or `"checksum": "<md5>"` to a `book.json`. The site does not publish unknown keys, but `book.json` itself is in the public repo, so the Drive ID, path or hash is public (PLAN §2, §5, §14).

**Verified.** Scratch script: `validateData` on a temp data dir whose book.json has exactly those three keys → `{"errors":[],"warnings":[]}`.

**Fix.** Also scan string values, recursively, for `drive.google.com` / `docs.google.com` URLs, `.epub` / `.kepub.epub` paths, and bare 32/40/64-hex strings (MD5/SHA-1/SHA-256). Optionally add `file`, `link`, `url`, `checksum` and `digest` to the key pattern. Report errors with the JSON path.

### R1-09 · low · `src/web/admin/edit-book-sheet.tsx:36-45`

**Problem.** The edit form keeps the user's edits in `state` (`useState`, frozen at open) but recomputes `initial` from the `book` prop on every data refresh. When the book changes on disk while the sheet is open, the diff therefore turns every untouched field back into the stale value.

**Failure scenario.** The edit sheet of book X is open. Meanwhile X's `book.json` changes: a bulk edit from another tab, `elib import`, a hand edit, or an agent. `elib:data-changed` → `refreshSiteData()` → a new `BookDetail` → a new `initial`. The "Salva modifiche" button becomes enabled with no user edit, and saving (or saving any other change) sends `{topic: <old>, status: <old>…}`. That silently reverts the external change and, for topic, title or authors, moves the Drive files back.

**Verified.** Pure-function repro with the real helpers: `diffToPatch(bookToFormState(refreshed), bookToFormState(opened))` → `{"topic":"unsorted","status":"to-read"}` although the user changed nothing. Not clicked through in a browser.

**Fix.** Freeze the baseline at open time (`const [initial] = useState(() => bookToFormState(book))`), so the patch only contains fields the user touched. Optionally show a notice "il libro è cambiato su disco" when `book` changes while the sheet is open.

### R1-10 · low · `src/node/services/mutex.ts`, `src/node/cli/program.ts:69-76`

**Problem.** Writes are serialized only inside one process. `elib sync`, `elib import` and the Hono server can run at the same time against the same `data/`, cache and Drive.

**Failure scenario.** With `pnpm dev` running, the user starts `elib sync --prune`. The CLI reads `data/books` first and lists Drive second. If a book is created through the UI in between (cover-only folder created after the CLI's read, files uploaded before its listing), the new book's files are classified as orphans and trashed, and then `book.json` is written. The book exists in the repo but its files are in the Drive trash, until the next `elib sync` re-uploads them from the cache. Concurrent moves (UI edit plus sync) produce spurious `rclone-failed` errors. A long `elib import` (Fase 5) alongside UI edits is the likely trigger.

**Verified.** By reading (ordering in `reconcile()` → `readAllBooks` then `listLibraryFiles`). Not reproduced.

**Fix.** Add a cross-process lock file (for example `<cache>/.lock` with `O_EXCL` + PID, or `proper-lockfile`) taken by every service write and by `sync`/`import`. Fail fast with a clear message ("il server locale sta scrivendo") instead of waiting forever.

## Bundle-size analysis + recommendation

Method: `vite build --sourcemap --outDir <tmp>`, then a script that decodes the source map and attributes each minified byte to its source package. Total 512.3 kB minified (161.5 kB gzip), one chunk:

| Package                                                                                                                                     | kB min | %    |
| ------------------------------------------------------------------------------------------------------------------------------------------- | ------ | ---- |
| react-dom (`react-dom-client.production.js`, production build)                                                                              | 202.4  | 40.4 |
| react-router (data router: `router.js` 45.7, `lib/dom`, hooks…)                                                                             | 96.1   | 19.2 |
| app code `src/web` (+11.0 shadcn `components/ui`, 1.2 shared)                                                                               | 49.2   | 9.6  |
| tailwind-merge                                                                                                                              | 26.7   | 5.3  |
| Radix primitives used (select 18.6, menu 9.4, collection 8.1, dialog, dismissable-layer, focus-scope, popper, roving-focus, dropdown-menu…) | ~68    | ~13  |
| @floating-ui (core/dom/utils/react-dom, via Radix popper)                                                                                   | ~21    | ~4   |
| react + scheduler + jsx-runtime                                                                                                             | ~11    | ~2   |
| lucide-react (tree-shaken: only the icons used)                                                                                             | 5.2    | 1.0  |
| react-remove-scroll, aria-hidden, use-sidecar… (Radix deps)                                                                                 | ~10    | ~2   |

What is **not** in it: zod (W3b kept the web modules zod-free), marked, fast-xml-parser, sharp, the `radix-ui` umbrella as a whole (only the imported primitives survive tree-shaking), all of lucide (5 kB), admin code. The suspected culprits are not the problem. About 60% is React DOM plus the React Router data router, which is the expected floor for this stack.

Recommendation (in order of value/effort):

1. **Long-term caching:** split vendors into their own chunks with `build.rolldownOptions.output.codeSplitting` (Vite 8 / rolldown; the warning links the docs). For example, groups for `react|react-dom|scheduler`, `react-router`, and `@radix-ui|@floating-ui|tailwind-merge|react-remove-scroll`. An app-only change then re-downloads only around 50 kB. Then raise `build.chunkSizeWarningLimit` to around 250 so the warning stays meaningful.
2. **Drop popper-based Radix from the first paint** (about 60 kB min, about 18 kB gzip):
   - the sort control (`library-toolbar.tsx`, Radix Select) → a styled native `<select>`;
   - the theme `DropdownMenu` (`theme-toggle.tsx`) → a 3-state cycle button or segmented `ToggleGroup`;
   - lazy-load the mobile filter `Sheet`.
     These are the only Radix popper users on public pages; admin keeps its own (lazy) chunk.
3. **Route-level `lazy`** for `book-page.tsx`: a small win, but it keeps the grid's first load lean as the book page grows.
4. Not worth it: swapping React for Preact (breaks Radix/shadcn assumptions), or dropping React Router (the declarative mode would lose `ScrollRestoration`, which W3b relies on).

Expected result: about 440 kB min / about 140 kB gzip on first load, plus good caching across deploys. The gzip size is already acceptable for a personal site.

  - KEPUB regeneration falls back to the pre-move path when the move failed;
  - a second run plans nothing (tested).
- **Dry run:** a dry-run rclone records writes only, and kepubify and downloads are skipped. The test asserts that remote, cache and data are unchanged. The `elib import --dry-run` code path writes nothing either.
- **Topic rename:** the label is written first, then a DirMove per tree when the target is absent (warning + file-by-file otherwise). A dry run simulates the moved listing. Idempotent through `elib sync` after a partial failure.
- **Server:** 127.0.0.1 only. Host allow-list (DNS rebinding). Origin allow-list, with Origin required on non-GET (covers cross-site forms, multipart, `text/plain` simple requests and `Origin: null`). `Sec-Fetch-Site` must be same-origin/none, no CORS headers, body limits (1 MB JSON, 200 MB + 1 MB EPUB, 20 MB + 1 MB image). `:id`, `uploadId` and `source` are validated (`isBookId`, UUID v4, allow-list), so there is no path traversal.
- **XML:** fast-xml-parser 5.12 entity expansion is bounded (probed: throws at 100 000 expanded chars). EPUB hrefs only index the in-memory zip map (no filesystem access). Chapter file names are slugified.
- **Privacy:**
  - `buildSiteData` publishes only known fields (unknown keys are never published);
  - MD5s are only compared in memory (never in `analysis.json`, the repo or the site);
  - Open Library requests send only ISBN/title/author with a generic UA;
  - `elib text` refuses an output inside the repo (realpath);
  - tests write only under `os.tmpdir()` (`git status` unchanged after the full suite and the build);
  - `dist/` has only `index.html`, `404.html`, assets and `data/`.
- **Write flows:**
  - create order is EPUB to cache → kepubify → cover → Drive → `book.json` last;
  - on failure the cover-only folder is removed;
  - the ID is reserved in `state.json`, and retries reuse it (no duplicate Drive files);
  - delete removes the repo folder only after the trash step has no errors;
  - patch/bulk preserve unknown keys;
  - ID uniqueness counts incomplete folders, cache dirs and reserved IDs;
  - `unsorted` cannot be deleted;
  - every service write runs under the mutex.
- **Site:**
  - clean URLs with basename `BASE_URL`;
  - `404.html` byte-identical to `index.html`;
  - raw HTML in Markdown is escaped;
  - the detail loader checks `v.id === id`;
  - book IDs are validated before fetching;
  - dev and build use the same URL layout.
